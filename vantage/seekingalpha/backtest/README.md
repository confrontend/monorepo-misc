# Seeking Alpha Quant Rating Backtest

This document is the self-contained interpretation manual for the application in this folder.
It is written so that a person or an AI agent can receive only:

1. this README, and
2. a screenshot from the application,

and still identify the screen, explain the visible numbers, understand how they were calculated,
and state the important limitations.

The application is a local research tool. It is not a brokerage, live trading system, portfolio
tracker, or investment recommendation service. Its purpose is to test whether Seeking Alpha Quant
Ratings contain useful information and whether explicit rating-based strategies would have worked
on the locally imported historical data.

The standard for this project is honest evidence. A result of "no demonstrated edge," "mixed," or
"insufficient data" is valid. Large returns must not be interpreted as proof until benchmark,
universe, outlier, multiple-testing, and timing effects have been considered.

**Before handing this file to anyone as standalone context, run `node scripts/check-readme.mjs`.**
Parts of this document are a dated snapshot: ticker counts, row counts, and the saved research
result all change the moment new files are imported or the research pipeline is re-run, and nothing
in the application announces that. The script compares this README's factual claims against the live
database, the saved run, the API surface, and the referenced source files, and exits non-zero if any
of them has drifted. It checks facts, not wording.

For chronological implementation history, decisions, test results, and unresolved work, read
[`../progress.md`](../progress.md). For the previous engineering handoff, read
[`docs/handover.md`](docs/handover.md). This README describes the current application behavior;
the progress log describes how it got here.

## 1. How an AI agent should answer questions about screenshots

When interpreting a screenshot, follow this order:

1. Identify the main area: ETFs or Data. Single-stock routes are retained only as archived compatibility routes.
2. If it is ETFs, identify the open workspace section: rule discovery, current ETF candidates, or statistical research.
3. Read every visible control before interpreting a number: rating family, persistence period, hold period, data period,
   and whether the result is exploratory, validated, or statistical evidence.
4. Identify the exact column or card label. Similar-looking percentages in different screens often
   answer different questions.
5. State whether the number is:
   - a stock return,
   - a market-adjusted/excess return,
   - a strategy return,
   - a hit rate,
   - a correlation,
   - a confidence statistic, or
   - an end-of-test snapshot.
6. Name the comparison baseline: the same stock bought and held, SPY, the dynamic eligible pool, or
   random tickers on the same dates.

### Navigation and canonical routes

The visible interface has two active top-level areas: ETFs and Data. The former Single Stocks area is
archived from navigation because its historical results were not reliable enough for the current ETF
decision workflow. Its code and direct routes remain available for historical investigation, but new
work should use the ETF workflow.

| Top-level area | Subview | Canonical route |
|---|---|---|
| ETFs | Combined rule discovery, current candidates, and statistical evidence | `/etfs` |
| Data | Import, consolidate, archive, and database status | `/data` |

Older ETF routes such as `/etfs/discovery`, `/etfs/research`, and `/etfs/check` are accepted as

### Why Single Stocks is archived

The single-stock screens were useful during exploration, but their historical universe and results were
not reliable enough to support the current decision workflow. They are therefore hidden rather than
deleted: the source, reports, and direct routes remain available for reproducibility and investigation.
The active workflow focuses on ETFs because the current goal is to discover, validate, and apply ETF
rating rules to the currently imported ETF universe.
7. Explain the time rule: same captured day, next available captured day, fixed horizon, rating
   change, or rebalance date.
8. Mention the relevant limitation from this README.
9. If a screenshot crops out required controls, say which missing control prevents a definite
   interpretation. Do not guess it.

### Example: "Why is this 8% higher?"

The answer depends on the label:

| Screenshot label | What "8% higher" means |
|---|---|
| Avg extra return | The strategy return minus the same ticker's buy-and-hold return, averaged across tickers. |
| Rating tier - S&P 500 | The average trailing return of the latest-rating group minus SPY's return. |
| Mean excess | The average trade return minus SPY over each trade's same dates. |
| What picking added / vs owning everything | Portfolio return minus the dynamic all-eligible-stock pool return. |
| Above SPY / vs SPY | Portfolio return minus SPY return. This includes any advantage already present in the selected survivor universe. |
| Since entry | Only the unrealized move of one position still open at the end, from its latest position entry/cost basis. |

Differences between percentage returns are percentage-point differences even when the UI displays
the `%` symbol. For example, 80% portfolio return minus 55% pool return is 25 percentage points,
not a 25% relative increase.

### Questions this README lets an agent answer

- Why can a stock be Strong Buy while its historical return is poor?
- Why can portfolio return be high while final holdings show `too new` or nearly 0%?
- Why can a strategy beat SPY but fail to beat the eligible pool?
- Why can a raw mean be positive while the trimmed mean is negative?
- Why can a grid cell clear a statistical bar but still fail the placebo control?
- Why do two screens show different hit rates?
- Why is a current rating not proof that it predicted the trailing return shown next to it?

## 2. What the application is trying to learn

The project separates several questions that must not be conflated:

| Question | Correct screen |
|---|---|
| What would a simple rating-driven trading policy have done for each ticker? | Stocks |
| Did those policies beat simply holding each ticker? | Overview |
| Were historical transitions into Strong Buy profitable until the next rating change? | Signal analysis -> Strong Buy trust |
| Do stocks with better latest ratings currently have stronger trailing histories? | Signal analysis -> Rating groups |
| Did a rating at the start of an episode predict the later market-adjusted direction? | Signal analysis -> Prediction accuracy |
| Which bullish rating-persistence rule was strongest before an unseen final-year check? | Signal discovery |
| Which bullish rating-persistence rule was strongest when the universe contains ETFs only? | ETF discovery |
| Did bullish-rated ETFs reliably beat SPY, and did waiting add value? | ETFs -> Research |
| Did stock bullish/bearish persistence produce a statistically defensible edge? | Single Stocks -> Research |
| What if many currently qualifying names were bought together and losers were replaced? | Portfolio |
| Which local files are actually in the database? | Data |

The screens intentionally overlap in subject matter but not in methodology. A disagreement between
screens is often informative rather than a bug. For example, a trailing latest-rating group can
look strong while fixed-horizon prediction accuracy remains close to chance.

## 3. Technology and runtime model

- Front end: React 18, TypeScript, Vite 6, hand-written CSS.
- Navigation: local React state, not a URL router.
- Remembered UI state: browser `localStorage` under `seeking-alpha-backtest-ui-state`.
- Local database: SQLite at `.data/vantage.sqlite`.
- Analysis engine: `src/data.ts`, loaded server-side and initialized from SQLite.
- API layer: Vite development-server middleware in `vite.config.ts`.
- Advanced research pipeline: Python files under `research/`.
- External runtime data calls: none during normal analysis. The app reads locally imported files and
  local cached benchmarks.

Important: `npm run build` creates static front-end assets, but the built `dist/` directory does not
contain the API/backend middleware. The complete application is currently intended to run through
`npm run dev`.

### Run the application

```bash
cd seekingalpha/backtest
npm install
npm run dev
```

Then open the Vite URL, normally `http://localhost:5173`.

Useful commands:

```bash
npm run build             # TypeScript check plus production front-end build
npm run preview           # Serve the built front end (no API: the endpoints are dev-server only)
npm run fetch:benchmark   # Refresh locally cached benchmark files
npm run consolidate:single # Merge cumulative single-folder bundles without deleting sources

node scripts/check-readme.mjs   # Verify this README still matches the code and the saved run
node scripts/fix-encoding.mjs   # Repair mojibake if source files were saved as Windows-1252
```

`npm run preview` serves the production build, but every API route in section 9 is Vite dev-server
middleware. A previewed or deployed build renders the shell and cannot load data. Use `npm run dev`
for anything involving numbers.

The normal data workflow is:

1. Put supported `.json` files anywhere under `input/`.
2. Start the application.
3. Open Data.
4. Press **Consolidate, archive & import** for cumulative `input/3-year/raw_*.json`,
   standalone ticker price/rating files directly under `input/3-year/`, and ticker quant-history
   captures directly under `input/`. Press **Import** for benchmarks and other ordinary captures.
5. Other screens calculate from the updated SQLite database.

No API key is required to read already downloaded data. The optional benchmark refresh script uses
Yahoo Finance and caches its result locally; it does not make every page load call Yahoo.

### Consolidating all replaceable ticker-source files

The upstream collector may write a new cumulative file under `input/3-year/` that repeats
most rows from older files. Run:

```bash
npm run consolidate:single
```

This maintains exactly one stable `consolidated_unique.json` and matching `.manifest.txt`. It merges
the cumulative bundles, individual three-year price/rating responses, and individual quant-history
captures. Files under `input/benchmark/` are explicitly outside this workflow and are never moved
or removed. Before removing anything, the script creates a timestamped ZIP under
`input/3-year/archive` and verifies every archived member. It then atomically replaces the
consolidated file and removes only the verified, locally archived ticker sources plus older
consolidations. It never stages or commits files to Git. If ZIP creation, source-stability, or output
verification fails, source files remain untouched.

The output keeps one wrapper per ticker and payload type (`prices`, `changes`, and `quant`) because
those are different required datasets. Price/rating API rows are deduplicated by stable API ID;
quant snapshots are deduplicated by ticker and date. If the same identity has different content,
the newest source wins; rows absent from a newer file are retained. Ticker metadata follows the
same rule, while an explicit `fundType` is not erased by a later price response that omits it.

The script atomically writes and rereads the result, records source/output SHA-256 hashes, and lists
upstream captcha/error payloads that contained no usable rows. Use `--dry-run` to inspect counts
without writing, or `--strict` to fail when any ticker/type has only invalid upstream responses.
Use `--keep-sources` to create and verify the local archive without deleting old inputs. Archive
files can be committed manually if desired, but Git is not part of the consolidation operation.

After each run, confirm the UI reports completion and a local archive. The manifest must say
`verified: true`; review `payloadsWithNoUsableUpstreamData` if it is non-empty. The UI action imports
the consolidated replacement into SQLite automatically after archival and cleanup.

The Data tab's **Consolidate, archive & import** button runs this complete command-line workflow as
a tracked backend job and then imports SQLite automatically. It displays the current stage,
percentage, symbol/ETF/row totals, removed-file count, and archive result. Reloading or returning to
Data resumes the current job display. The separate **Import** button remains for benchmarks,
nonconsolidated input files, and retrying SQLite import if archival succeeded but database import
was temporarily locked.

## 4. End-to-end data flow

```text
input/**/*.json
    -> Data screen / POST /api/data/import
    -> server/db/ingest.ts detects each file by content
    -> .data/vantage.sqlite stores normalized raw observations and provenance
    -> server/db/datasets.ts reconstructs one daily dataset per ticker
    -> src/data.ts calculates the standard application screens
    -> /api/analysis returns the selected result
    -> React renders tables, conclusions, details, and portfolio simulations

.data/vantage.sqlite
    -> research/run_analysis.py
    -> research/pipeline.py
    -> research/report/*.csv and run_meta.json
    -> /api/research
    -> Research lab
```

### Supported input shapes

Files are identified by their contents, not their names or folder path.

| File kind | Meaning |
|---|---|
| Daily rating snapshot (`capture`) | One ticker with daily price, rating, score, and sometimes factor grades. |
| API prices (`api_prices`) | Seeking Alpha historical OHLCV plus `div_adj_factor`. |
| API rating changes (`api_changes`) | Point-in-time rating transitions and numeric old/new rating scores. |
| Bundle (`bundle`) | Multiple raw API price/change responses in one JSON array. |
| Benchmark (`benchmark`) | Locally cached market/ticker daily close and adjusted close data. |

Dates are normalized to `YYYY-MM-DD` during import.

### Canonical raw database tables

| Table | Main purpose |
|---|---|
| `source_files` | File path, SHA-256, import status, row counts, error, and import time. |
| `tickers` | Ticker slug and available metadata such as company, exchange, currency, and sector. |
| `prices` | Daily OHLCV, dividend adjustment factor, and stored adjusted close. |
| `rating_changes` | Rating transition date, old/new rating labels and scores, and contextual fields. |
| `quant_history` | Daily snapshot price, rating, score, and factor grades. |
| `benchmark_prices` | Cached close and adjusted close for SPY and ticker benchmarks. |
| `data_version` | A single version number incremented after meaningful imports. |

Every raw row references its source file. The source JSON remains the audit artifact; raw JSON is
not duplicated into every database row.

The database also provides `historical_prices` and `ticker_changes` compatibility views for the
Python research pipeline.

### Adjusted prices

For API historical prices, import stores:

```text
adjusted close = close x div_adj_factor
```

Reconstructed ticker datasets use this adjusted close. Snapshot-only datasets retain their captured
price, whose adjustment basis is not guaranteed. Independent buy-and-hold comparisons use locally
cached adjusted benchmark prices when available.

### Reconstructing daily rating history

For a ticker with API prices and rating-change events:

1. Sort prices and rating changes by date.
2. For each price date, apply the latest rating change known on or before that date.
3. Before the first recorded change, use that change's `previous_rating` and previous numeric score
   only when both are present.
4. Drop unknown ratings, null ratings, `-`, and other noncanonical values.

Seeking Alpha's source taxonomy is mapped as follows:

| Source value | Application label | Direction used in tests |
|---|---|---|
| `very_bullish` | Strong Buy | Bullish |
| `bullish` | Buy | Bullish |
| `neutral` | Hold | Neutral |
| `bearish` | Sell | Bearish |
| `very_bearish` | Strong Sell | Bearish |

If a ticker lacks usable API price/change history but has usable daily captures, it is loaded as a
snapshot-only dataset. The current application uses one unified database-backed ticker universe
across the standard analysis screens.

### Import behavior

- Scanning is recursive under `input/`.
- SHA-256 detects real content changes.
- Re-importing unchanged files is idempotent.
- A failed file is reported with its error; other files can still import.
- Moving/deleting a source file does not automatically delete its already imported rows.
- A successful material import increments `data_version` and invalidates in-memory analysis caches.

SQLite uses `TRUNCATE` journal mode, not WAL, because WAL has corrupted/reopened unreliably on the
Windows/WSL/FUSE environments used for this project. Result snapshot persistence is disabled by
default and can be enabled with `VANTAGE_PERSIST_RESULTS=1`; the UI normally calculates on demand.

## 5. Global interpretation rules

### Rating versus score

`Quant Rating` is one of five categories. `Quant Score` is the numeric value used to order stocks
within eligible groups. A Strong Buy badge means the source's rating category at that date; it does
not mean the application itself guarantees a profitable trade.

A stock can be Strong Buy and still show a poor historical result because:

- the badge is the latest/current rating while the return can cover an earlier period;
- the rating may have changed after losses already occurred;
- the stock may be strong relative to peers but still decline in a weak market;
- a strategy can enter too late or exit too early;
- the current universe and historical sample can be biased;
- one stock's result can simply be noisy.

### Raw return versus excess return

```text
raw return = stock ending price / stock starting price - 1
excess return = stock or strategy return - SPY return over the same dates
```

A bullish stock gaining 8% while SPY gains 12% has a raw return of +8% but an excess return of
-4 percentage points. Market-adjusted correctness treats that as a failed bullish call.

### Hit rate

Hit rate always means `correct observations / scored observations`, but the definition of one
observation differs by screen. Never compare hit rates until the observation type is identified.

### Average versus median

- Average uses every value and can be dominated by a few extreme winners.
- Median is the middle observation and better represents a typical case.
- A positive average with a negative median is an outlier warning.
- Trimmed/winsorized/geometric means on the Strong Buy screen are additional robustness checks.

### Growth of $100

Growth of $100 is a sequential portfolio replay, not the same calculation as an average call
return. If each completed trade reinvests the previous result, returns compound. A table can
therefore show modest individual returns but a larger final dollar value.

### Entry timing is screen-specific

| Screen | Entry timing |
|---|---|
| Stocks replay | Uses the captured record price when the replay changes position. This is an exploratory replay and can use the same observed day. |
| Strong Buy trust | Enters on the next usable record after the transition into Strong Buy. |
| Prediction accuracy | Enters on the next usable record after a rating episode starts. |
| Research lab — bullish persistence | Enters on the first qualifying persistence-event date in its trading-day timeline, using the older study's same-day adjusted close. |
| Research lab — bearish families | Treats the rating date as a signal and enters on the first available stock session strictly after it. |
| Portfolio | A signal decided on date D is executed on the next available captured date. |

This difference is important. Results from these screens are not interchangeable.

### Transaction costs

Transaction costs, bid/ask spread, slippage, taxes, borrow costs, and market impact are not deducted.
Reported trading returns are gross. High-turnover weekly portfolio configurations are especially
likely to look better in the application than they would after real execution costs.

## 6.2 Stocks

### Question answered

"For each ticker, what would an explicit rating-driven policy have done over the selected history,
and how does that compare with simply holding the stock?"

### Controls

- Signal history: trailing window ending at the latest available date (`7d`, month windows, or all).
- Signal policy:
  - Exit on Hold: long on Buy/Strong Buy; cash on Hold/Sell/Strong Sell.
  - Hold through Hold: long on Buy/Strong Buy; remain long through Hold; cash on Sell/Strong Sell.
  - Long-short: long on Buy/Strong Buy; cash on Hold; short on Sell/Strong Sell.
- Sort rows: hit rate, average return, number of signals, or ticker.

### Backtest by ticker columns

| Column | Exact meaning |
|---|---|
| Ticker | Symbol and company name. |
| Signals | Number of non-neutral historical records eligible for the terminal-return signal summary. |
| Latest rating | Last rating inside the selected history window. |
| Hit rate | Share of those signal records whose directional return to the window's final record was positive. |
| Avg return | Average directional return from each eligible record to the final record. |
| Median return | Median of those same terminal-anchored directional returns. |
| Growth of $100 | Ending value of the separate sequential position replay. |
| Buy & hold | Ending value of $100 invested in cached adjusted ticker prices for the same window. |
| Rating changes | Count of transitions between rating categories inside the window. |
| Date range | First and final captured dates in the selected window. |

Critical distinction: `Avg return`, `Median return`, and `Hit rate` use many overlapping observations
that all end at the same final record. `Growth of $100` uses the position-changing replay. They are
not expected to reconcile numerically.

### Strategy matrix action

The matrix compares every available history window x the three policies for one ticker. It marks the
largest and smallest displayed ending values as Best and Worst. Best means best inside that matrix,
not statistically validated and not guaranteed out of sample.

### Full detail panel

- Starting/ending value and total return: sequential replay.
- Position: open long, open short, or closed at the end.
- Buy & hold: independent adjusted-price benchmark.
- Entries/exits: number of position changes.
- Rating distribution: captured days in each rating.
- All decisions: rating transitions and the replay's action at each transition.
- Exit return: return for the position closed by that event; blank for entries/hold decisions.

### Limitations

- The terminal-anchored signal observations overlap and are exploratory, not independent tests.
- The replay does not deduct costs.
- Same-day captured entry prices are less conservative than the next-day rule used by the stronger
  prediction and portfolio tests.
- Benchmark coverage can be missing for a ticker.

## 6.3 Overview

### Question answered

"Across all benchmarked tickers, which history-window and policy combinations beat simply holding
each stock?"

### Columns

| Column | Meaning |
|---|---|
| Signal history | Window tested. |
| Signal policy | Position rule tested. |
| Tickers tested | Tickers with a usable buy-and-hold benchmark / total loaded tickers. |
| Beat holding | Count and percentage where strategy return exceeded that ticker's buy-and-hold return. |
| Avg extra return | Average of `strategy return - buy-and-hold return`. |
| Median extra return | Middle extra return across tickers. |
| Avg strategy | Mean sequential replay return. |
| Avg buy & hold | Mean passive ticker return. |
| Confidence | Low under 10 tickers, Medium from 10, High from 30. This is a sample-size label, not a statistical confidence interval. |
| Verdict | Good, Mixed, Poor, or Not enough data using the thresholds below. |

Verdict rules:

- Good: average and median extra return above zero and at least 60% beat holding.
- Poor: average and median extra return below zero and at most 40% beat holding.
- Mixed: anything between those rules.
- Not enough data: fewer than three tested tickers.

The table inherits all limitations of the Stocks replay. It is a descriptive comparison, not the
project's strongest predictive-evidence screen.

## 6.4 Signal analysis -> Strong Buy trust

### Question answered

"When a ticker newly entered Strong Buy, was buying on the next usable day and holding until it left
Strong Buy profitable?"

### Trade rule

1. Ignore repeated Strong Buy days.
2. Detect a transition from any non-Strong-Buy rating into Strong Buy.
3. Enter on the next usable record, not the transition day's price.
4. Exit on the first later record whose rating is not Strong Buy.
5. If it never exits before the dataset ends, mark it Open.
6. Do not invent an entry for a ticker already Strong Buy at the left edge of captured history.

### Columns

| Column | Meaning |
|---|---|
| Completed | Calls with both an entry and exit. |
| Wins / Losses | Positive versus non-positive effective call return. |
| Win rate | Wins divided by completed calls. |
| Avg/Median call return | Uses excess return over SPY when benchmark dates exist; otherwise raw stock return. |
| Growth of $100 | Compounds raw stock-price returns across completed calls and marks an open call at the last captured price. |
| Open call | Raw return so far for the current unclosed call. |

Important: Growth of $100 is based on raw stock growth, while win rate and average/median call return
prefer market-adjusted excess return. Those columns can disagree without a calculation bug.

### Outlier and concentration panel

- Raw mean: ordinary average effective return.
- Median: typical middle call.
- 10% trimmed mean: removes the top and bottom 10% before averaging.
- Winsorized mean: caps extremes rather than removing them.
- Geometric mean: average compounded growth rate when mathematically valid.
- Top 1/5/10% contribution: share of positive profit supplied by the best calls.
- Leave-one-ticker-out range: recalculates the mean after removing each ticker in turn.
- Outlier-sensitive: triggered when robust results change the sign, top 10% dominates at least half
  of positive profit, or removing one ticker flips the sign.

This screen only sees tickers in the current imported universe. It cannot include historical stocks
that disappeared from Seeking Alpha coverage before the exports were created.

## 6.5 Signal analysis -> Rating groups

### Question answered

"Do stocks grouped by their latest available rating have stronger or weaker trailing performance?"

This is not a point-in-time prediction test. It groups each ticker by its latest rating and looks
backward at historical returns. Because momentum is itself part of Quant Rating, separation can be
partly mechanical.

### Quant score vs excess return

Each dot is one ticker:

- X-axis: latest/current numeric Quant Score.
- Y-axis: the ticker's full tracked buy-and-hold return minus SPY over the same dates.
- Color: latest rating tier.
- `r`: Pearson correlation across tickers.
- Trend line: simple linear regression.

This combines a latest score with a full historical trailing return. It is descriptive, not causal.
If scores barely vary within a tier, the correlation mainly reflects differences between rating
tiers rather than fine score differences such as 4.1 versus 4.9.

### Win rate vs S&P 500

For each latest-rating tier, the bar shows the share of tickers whose full tracked return beat SPY
over that ticker's exact same dates.

### Rating tier vs S&P 500

For each trailing window:

```text
tier cell = average return of tickers whose latest rating is that tier
displayed value = tier cell - SPY return for the window
```

The sample count shows usable tickers / all tickers currently in that tier.

### Real performance by individual ticker

Each cell is that ticker's own trailing buy-and-hold return for the selected window. It is grouped
under the ticker's latest rating; it is not the return earned after that latest rating was issued.

### Common screenshot question

"Why is a stock Strong Buy but its 12-month return is negative?" Because Strong Buy is the latest
rating. The 12-month cell includes months before that latest rating and measures trailing stock
performance, not the outcome after the current rating.

## 6.6 Signal analysis -> Prediction accuracy

### Question answered

"When a rating episode began, did its original directional call correctly predict the stock's later
market-adjusted direction?"

Available forward horizons are 30, 90, 180, and 365 calendar days.

### Rating episodes

An episode starts when a ticker's rating category changes. The first observed episode can be marked
left-truncated because its true beginning may predate captured history. Entry is the next usable
record after the episode begins.

### Primary fixed-horizon conclusion

- Hold the original episode rating fixed for the selected horizon, even if the live rating changes.
- Find the usable record closest to entry date + horizon within +/-7 calendar days.
- If no match exists, mark the outcome right-censored rather than a win or loss.
- Bullish is correct when stock return minus SPY return is positive.
- Bearish is correct when stock return minus SPY return is negative.
- Hold is neutral and excluded from headline directional hit rates.
- If SPY coverage is missing, the code falls back to absolute return and marks the call as not
  market-adjusted.

This answers prediction, not active trading behavior.

### Strategy-style rating-call conclusion

This related test exits at the earlier of:

- the next rating change, or
- the selected maximum horizon after entry.

It answers what would happen when reacting to each rating change. It must not be substituted for the
fixed-horizon predictive result.

### Statistics

| Metric | Meaning |
|---|---|
| Scored | Directional episodes with a valid future outcome. |
| Correct | Market-adjusted direction matched the original rating. |
| Hit rate | Correct / scored. |
| Wilson 95% CI | Descriptive binomial interval that assumes independent calls. |
| Ticker-cluster bootstrap 95% CI | Primary interval; resamples whole tickers so repeated calls from one ticker remain grouped. |
| Ticker-weighted hit rate | Compute each ticker's hit rate, then average tickers equally. |
| Median excess return | Middle stock-minus-SPY return. |
| Censored | Future horizon falls outside usable history. |

The frozen methodology currently uses 5,000 bootstrap repetitions with seed `20260804`. Multiple
testing correction has not yet been applied to every horizon/tier/policy result on this screen, so
individual combinations remain exploratory.

### Exploratory scatter and per-ticker table

The scatter uses one point per historical day, not one independent episode. Consecutive points have
heavily overlapping forward windows. Correlation `r` and slope are useful pattern indicators but
overstate evidence if read as independent tests. The primary episode-based conclusion above is the
more defensible result.

## 6.6a Signal discovery

Route: `/stocks/signal-discovery`.

This screen discovers a single-stock rating rule instead of asking the user to invent one. It tests
24 fixed rules: `Strong Buy` and `Buy or Strong Buy`, each continuously present for 30, 60, 90, or
180 calendar days, followed by a fixed 30-, 90-, or 180-day hold.

- Only one signal is emitted per continuous qualifying episode.
- The signal date is not tradable. Entry is the next usable stock record.
- The exit must land within seven calendar days of the fixed target; incomplete observations are
  excluded rather than shortened.
- Only the latest three years are used. The first two years discover/rank rules; the final year is
  unseen validation.
- Discovery outcomes must finish before validation starts, preventing validation-period prices from
  leaking into rule selection.
- Discovery rank uses median excess return over an equal-weight pool of other stocks carrying the
  same bullish rating family on that date. This is leave-one-ticker-out: the signal ticker is
  excluded from its own pool so its return cannot dilute its measured excess toward zero.
- A rule survives validation only if validation contains at least 15 tickers, median excess is
  positive versus both the rating pool and SPY, and more than half the observations beat the pool.
- The page selects the highest discovery-ranked rule that clears those fixed validation checks. It
  does not select whichever rule happened to have the largest validation return.

If no rule survives, the correct headline is `No rule survived validation`; the app does not promote
the least-bad rule. The ticker checker is available only when a rule survives. It compares the latest
imported rating streak with that frozen rule and does not produce a recommendation.

The result remains exploratory, gross of costs, and survivor-only. The final-year check reduces
time-selection leakage but does not repair missing delisted or dropped-coverage companies.

### ETF discovery

Route: `/etf-discovery`.

This subsection is the complete interpretation contract for ETF Discovery and its JSON export. An
agent should not need the source code to understand what a field means, how the winner was selected,
or which conclusions are allowed.

#### Question and universe

ETF Discovery asks two separate historical questions:

1. Did a bullish Seeking Alpha Quant rating identify ETFs that subsequently performed better than
   contemporaneous controls?
2. Did waiting for that bullish rating to persist add value beyond buying the matching bullish ETF
   pool immediately?

The universe contains only imported tickers whose normalized metadata has `fundType: "ETF"`.
`fundType` is stored as `tickers.fund_type`. Missing fund type, stocks, and depository receipts are
excluded; the screen never falls back to stock data. `universeTickers` in the export is the count
that entered this ETF universe before rule-specific eligibility checks.

A usable daily record must have a finite positive price, a finite Quant score, and one canonical
rating: `Strong Buy`, `Buy`, `Hold`, `Sell`, or `Strong Sell`. Reconstructed API histories use the
stored adjusted close. Snapshot-only histories retain the source's captured price, whose adjustment
basis may be unconfirmed. This mixed price-basis limitation applies to every raw return below.

#### Fixed rule grid

The system tests exactly 24 combinations:

- Rating filter: `strong-buy` or `bullish-plus`.
- Persistence: 30, 60, 90, or 180 calendar days.
- Hold: 30, 90, or 180 calendar days.

`strong-buy` accepts only `Strong Buy`. `bullish-plus` accepts either `Buy` or `Strong Buy` and does
not reset when the rating moves between those two levels. Each continuous qualifying episode emits
at most one signal: the first usable record whose calendar-day streak reaches the required
persistence. A later signal requires the rating to leave the filter and begin a new episode.

The signal date itself is not tradable. Entry is the next usable ETF record strictly after the
signal. The target exit is `entry date + holdDays`; the engine chooses the usable record closest to
that target within plus or minus seven calendar days. If no complete exit exists, the observation is
dropped. It never substitutes the final available date or silently shortens the requested hold.

For one completed observation:

```text
raw return (%)       = ((exit price / entry price) - 1) * 100
excess vs SPY (pp)   = raw return - matched SPY return
excess vs pool (pp)  = raw return - matched rating-pool return
```

`pp` means percentage points. A raw return of 9% and a baseline return of 4% produces +5pp excess,
not a 5% relative ratio.

#### Time split and prevention of look-ahead

`validationEnd` is the latest usable date in the imported ETF universe. `splitDate` is 365 calendar
days before it. `discoveryStart` is three 365-day years before `validationEnd`.

- Discovery includes signals on or after `discoveryStart` only when their completed exit is strictly
  before `splitDate`.
- Validation includes signals on or after `splitDate`, again only with a complete fixed-horizon
  exit.
- Signals before the split whose outcomes extend into validation are excluded from discovery. This
  prevents validation-period prices from helping rank a rule.

The earlier period ranks the rules. The final year checks the already-ranked rules. Validation
performance never changes `discoveryRank`.

#### Matching rating pool and SPY baseline

For each signal, the matching pool is built at that signal's date from other ETFs in the imported
universe:

1. Exclude the signal ETF itself (leave-one-ticker-out).
2. Use the most recent rating on or before the signal date only if it is no more than 10 calendar
   days old.
3. Require the same rating family as the rule: only Strong Buy for `strong-buy`, or Buy/Strong Buy
   for `bullish-plus`.
4. Enter every eligible peer on its next usable record and give it the same fixed hold horizon and
   seven-day exit tolerance.
5. Arithmetic-mean the peer returns. That mean is the signal's `poolReturn`.

SPY uses locally cached adjusted-close quotes on or before the signal ETF's entry and exit dates.
If a required pool or SPY observation is unavailable, the corresponding excess statistic excludes
that comparison rather than treating it as zero.

#### Per-period summary fields

Every rule has a `discovery` object and a `validation` object with the same fields:

| Field | Exact meaning |
|---|---|
| `observations` | Number of completed qualifying episodes. One ETF can contribute multiple episodes. |
| `tickers` | Number of distinct ETFs represented by those observations. This is the breadth check. |
| `medianReturn` | Median raw ETF return, in percent. |
| `medianExcessSpy` | Median of each observation's paired ETF-minus-SPY difference, in percentage points. |
| `medianExcessPool` | Median of each observation's paired ETF-minus-pool difference, in percentage points. |
| `positiveRate` | Fraction of raw returns greater than zero, from 0 to 1. |
| `beatPoolRate` | Fraction of available paired pool comparisons whose excess is greater than zero, from 0 to 1. |

Medians of paired differences are calculated observation by observation. They are not obtained by
subtracting two independently calculated headline medians, so `medianReturn - poolMedianReturn`
need not equal `medianExcessPool`.

#### Exploratory ranking and practical-gate statuses

Rules are ranked before validation is interpreted:

1. Higher discovery `medianExcessPool` ranks first.
2. A tie is broken by higher discovery `beatPoolRate`.
3. `discoveryRank` is one-based; 1 is the strongest discovery-period rule.

The descriptive table then assigns a practical-gate status:

- `too-thin`: discovery or validation contains fewer than 15 distinct ETFs.
- `survived-validation`: not thin, validation `medianExcessPool > 0`, validation
  `medianExcessSpy > 0`, and validation `beatPoolRate > 0.5`.
- `failed-validation`: enough ETFs, but one or more validation conditions failed.

`bestRule` is the smallest `discoveryRank` whose status is `survived-validation`. It is not the rule
with the largest validation return. If none survives, `bestRule` is `null`.

These fields are retained for exploration and continuity with stock Signal Discovery. They are not
the ETF evidence verdict: validation is inspected for all 24 rows and therefore is not untouched for
this practical-gate winner. The UI labels this section **Exploratory** and renders
`survived-validation` as **Passed practical gate**.

#### Where the formal ETF verdict lives

ETF Discovery is intentionally exploratory. Its 24-row persistence search helps generate and inspect
possible rules, but it is not the final answer to whether Seeking Alpha's ETF ratings are trustworthy.
The formal, corrected evidence is in **ETFs > Research** (`/etfs/research`) and is generated by the
Python pipeline under the frozen `research/ETF_PRESPEC.md` specification.

That report keeps two questions separate:

1. **Rating trust (primary):** when an ETF newly enters Strong Buy, or Buy/Strong Buy, does it beat
   SPY over 30, 90, or 180 calendar days? These six cells are one correction family.
2. **Persistence improvement (secondary):** after an ETF remains continuously bullish for 30, 60,
   90, or 180 days, does it beat other ETFs carrying the same bullish rating? These 24 cells are a
   separate correction family.

Both use next-observed-session entry, complete fixed calendar-day horizons, at least 15 distinct ETF
clusters, 4,999 wild cluster bootstrap-t repetitions, separate Holm and BH correction, concentration
diagnostics, and a same-date random-ETF placebo for the strongest cell. A cell is marked positive
evidence only when `|t| >= 3` and Holm-corrected `p < 0.05`; the placebo is shown separately and must
also be read before making a conclusion. Results are validation-year, gross-of-cost, survivor-universe
evidence—not recommendations or guaranteed returns.

#### Descriptive matched controls

`trustTest` exists only when an exploratory ETF `bestRule` exists and complete matched controls are
available. It is descriptive and does not override the Research Lab ETF report. It uses that practical-gate
rule's validation observations and hold length. Each retained observation supplies four layers:

1. `spyMedianReturn`: SPY market baseline.
2. `nonBullishMedianReturn`: arithmetic-mean pool of ETFs rated Hold, Sell, or Strong Sell on the
   same date, using the same freshness, entry, exit, and leave-one-out rules.
3. `poolMedianReturn`: matching bullish rating pool for the winning filter.
4. `winnerMedianReturn`: raw return of the ETF that also met the winning persistence rule.

The paired comparison fields are:

| Field | Exact meaning |
|---|---|
| `poolMedianExcessSpy` | Median of bullish-pool return minus SPY return. |
| `poolMedianExcessNonBullish` | Median of bullish-pool return minus non-bullish-pool return. |
| `winnerMedianExcessPool` | Median of winner ETF return minus bullish-pool return. |
| `winnerMedianExcessSpy` | Median of winner ETF return minus SPY return. |
| `poolBeatSpyRate` | Fraction of matched cases where bullish pool return exceeded SPY. |
| `poolBeatNonBullishRate` | Fraction where bullish pool exceeded the non-bullish pool. |
| `winnerBeatPoolRate` | Fraction where the persistence-qualified ETF exceeded its bullish pool. |
| `winnerBeatSpyRate` | Fraction where the persistence-qualified ETF exceeded SPY. |

`ratingSupported` is true only when at least 15 distinct ETFs are represented,
`poolMedianExcessSpy > 0`, `poolBeatSpyRate > 0.5`, `poolMedianExcessNonBullish > 0`, and
`poolBeatNonBullishRate > 0.5`. `ruleAddsValue` is true only when the same breadth floor is met,
`winnerMedianExcessPool > 0`, and `winnerBeatPoolRate > 0.5`.

The `verdict` mapping is exact:

| Verdict | Meaning |
|---|---|
| `rating-and-rule-supported` | Both `ratingSupported` and `ruleAddsValue` are true. |
| `rating-supported-rule-not-supported` | Rating support is true; persistence did not clear its gate. |
| `rating-not-supported` | Rating support failed, regardless of the persistence result. |

The UI adds the phrase “passed narrowly” when the verdict supports both layers but the weakest of
`poolBeatSpyRate`, `poolBeatNonBullishRate`, and `winnerBeatPoolRate` is below 0.60. That wording is
an explanatory caution, not another methodology gate and is not stored as a separate export field.
The section is titled **Descriptive matched controls** and its badge says **Practical threshold**;
neither is a statistical trust claim.

#### ETF Discovery JSON export contract

Click **Export analysis** above All discovered rules. The file is
`etf-discovery-analysis.json`. It is a JSON object, not a bare table array:

| Top-level field | Meaning |
|---|---|
| `schemaVersion` | Export-envelope version. Currently 3. |
| `exportType` | `etf-signal-discovery`. Prevents confusing this file with stock discovery. |
| `exportedAt` | Time the browser created the file. |
| `resultGeneratedAt` | Time the analysis result was calculated. |
| `universe` / `universeTickers` | `etf` and the ETF count used by the run. |
| `periods` | Exact `discoveryStart`, `splitDate`, and `validationEnd` for this run. |
| `rulesTested` | Expected to be 24 for the current fixed grid. |
| `methodology` | Machine-readable timing, pool, exploratory selection, and descriptive trust rules. Version 4 explicitly delegates formal ETF evidence to Research Lab. |
| `bestRule` | Exploratory practical-gate rule, or `null`. It is not a formal verdict. |
| `trustTest` | Descriptive matched-control summary for `bestRule`, or `null`. |
| `displaySort` | UI column and direction in effect when exported. |
| `rules` | All 24 summarized rules in the displayed order. Use `discoveryRank` for canonical research order. |
| `tickerMatches` | Latest imported streak check against `bestRule`; this is a current-data screen, not a recommendation. |

For one rule, `filter`, `persistenceDays`, and `holdDays` identify the tested combination;
`discoveryRank`, `discovery`, `validation`, and `status` carry the fields defined above. For one
`tickerMatches` row, `persistenceDays` is the latest continuous qualifying streak,
`qualifies` means that latest streak meets `bestRule`, and `latestDate` identifies how stale that
statement may be.

`null` means the statistic could not be calculated or no winner exists. It never means zero.
Percentages are stored as numbers: `9.14` means +9.14%, while rates are fractions: `0.57` means 57%.

The export contains complete summary-level evidence and methodology, but not every raw daily price
or observation-level trade. It is sufficient to interpret, compare, sort, critique, and report the
run. Recomputing every value from first principles requires the imported SQLite/input data as well.

#### Allowed conclusion and limitations

Use the two ETF families in Research Lab—not `bestRule.status` or `trustTest.verdict`—for headline
evidence claims. An exploratory ETF winner means only that one pre-ranked persistence rule cleared
practical final-year thresholds. It is not a current buy list. `tickerMatches` only says which latest
imported streaks fit that exploratory rule.

All results are gross of commissions, spread, slippage, tax, and liquidity constraints. The local
universe may omit delisted or dropped-coverage ETFs and may overrepresent ETFs still covered when
the files were exported. Rating publication timing is approximated by next-record entry. The formal
Research Lab accounts for repeated episodes by resampling whole ETF clusters, corrects each frozen
ETF family separately with Holm and BH, and runs placebo/concentration diagnostics. It still cannot
repair survivor bias, unconfirmed capture-price adjustment, trading
costs, liquidity, or data-provider publication timing. Those limitations must accompany any claim.

## 6.7 ETF workspace and research

The `/etfs` page is the single active ETF workflow. It contains three collapsible sections:

1. **Discover and validate ETF rules** — the exploratory 24-rule holdout search chooses a practical
   persistence pattern using the earlier period and checks it on the final year.
2. **Current ETF candidates** — every imported ETF that currently matches a confirmed rule, with its
   current rating streak, required hold, historical edge, and verdict. This is the operational list,
   not a guarantee or an automatic order.
3. **Statistical evidence and diagnostics** — the corrected rating-trust and persistence families,
   including SPY comparisons, clustered bootstrap results, concentration checks, placebo tests, and
   the frozen methodology.

The same Python run still produces the stock studies for archival access, but they are not part of the
visible workflow. ETF discovery, candidate checking, and formal research now share one page so the
user can move from historical rule discovery to current candidates without switching contexts.
The bearish rules are frozen in `research/BEARISH_PRESPEC.md`. Exploratory bearish numbers were seen
before that document was written, so the first bearish report is a frozen durable implementation,
not a blind pre-registration.

### ETF rating trust and persistence improvement

The ETF rules are frozen in `research/ETF_PRESPEC.md`. Earlier exploratory ETF results were already
known when it was written, so this is a fixed, auditable methodology rather than a claim of blind
pre-registration. Only imported tickers whose normalized `fund_type` is `ETF` enter these families.
Both use the final 365 calendar days of available ETF prices as validation data.

The two questions and benchmarks are deliberately different:

| Family | Main question | Grid | Primary tested value |
|---|---|---:|---|
| Rating trust | Do newly bullish-rated ETFs beat SPY? | 2 rating filters x 3 holds = 6 | ETF adjusted return minus SPY adjusted return |
| Persistence | Does waiting add value after an ETF is already bullish? | 2 filters x 4 persistence periods x 3 holds = 24 | ETF adjusted return minus the same-date matching bullish ETF pool |

The rating filters are Strong Buy only and Bullish+ (Buy or Strong Buy). Holds are 30, 90, and 180
calendar days. Persistence periods are 30, 60, 90, and 180 calendar days. Rating trust emits a signal
only when an observed prior nonqualifying rating changes into the selected family; the first rating
in a ticker history cannot count as a transition. Persistence emits once when each continuous bullish
episode first reaches the requested age.

Entry is the first usable ETF price strictly after the signal. Exit is the closest usable price to
`entry + hold`, limited to plus or minus seven calendar days. A trade without that complete horizon
is excluded rather than shortened. SPY is measured over exactly the same entry and exit dates. The
persistence pool contains other ETFs in the same bullish rating family at the signal date; the ETF
being judged is excluded from its own benchmark.

Each family independently requires at least 15 distinct ETF clusters and uses 4,999 wild cluster
bootstrap-t repetitions. Holm and Benjamini-Hochberg corrections are applied within the six-cell or
24-cell family, never across the two questions or across stock research. The displayed evidence bar
is `|t| >= 3` and Holm `p < 0.05`. The strongest cell also receives a same-date random-ETF placebo and
a concentration check. Clearing the numerical bar without separating from the placebo is not enough
to attribute the result to the rating.

#### Current saved ETF result

The checked-in report covers 321 ETFs, 232,765 ETF price rows, and 16,758 rating events. Validation
runs from 2025-08-07 through 2026-08-07.

- **Rating trust:** 4 of 6 cells clear the corrected numerical bar. The strongest is Bullish+ held
  90 days: 1,062 complete observations across 240 ETFs, average ETF return +11.64%, average SPY return
  +5.51%, and average edge +6.13 percentage points (clustered 95% interval +4.87 to +7.43pp;
  Holm `p = 0.0012`). It also separates from the same-date random-ETF placebo (`p = 0.0005`). This is
  positive historical evidence that the broad bullish ETF rating family beat SPY in this validation
  year and imported universe.
- The Research UI also shows ten chronological completed examples from that strongest cell. Each
  example includes the signal date, next-session buy date and adjusted price, rule-based sell date
  and adjusted price, actual days held, ETF return, SPY return over the same dates, and what $100
  became. They explain how to apply the rule; they are not the ten best trades and do not replace
  the aggregate result.
- **Persistence improvement:** 1 of 24 cells clears the corrected numerical bar. Bullish+ sustained
  for 30 days and then held 30 days produced 387 complete observations across 254 ETFs. Average edge
  over the matching bullish ETF pool was +1.24pp (clustered 95% interval +0.59 to +1.97pp;
  Holm `p = 0.0096`) and its placebo passed (`p = 0.0005`). This supports a smaller, separate claim:
  waiting 30 days added value in that cell. It is not required for the rating-trust result to be true.

These are gross historical results from a survivor-filtered imported universe. They do not include
costs, liquidity, taxes, or a live point-in-time ETF universe, and they are not a current buy list.
The authoritative machine-readable files are `research/report/etf_meta.json`,
`etf_rating_trust_results.csv`, `etf_persistence_results.csv`, their concentration CSVs, and their
placebo CSVs. `/api/research` loads them for the Research Lab UI.

### Bearish / short research

#### Questions answered

1. After a rating newly crosses into Sell or Strong Sell, does an outright short make money?
2. After a rating has stayed bearish for 3, 6, 12, or 18 months, does an outright short make money?
3. Does the bearish stock at least underperform SPY, even when its own price still rises?

The first and second questions are different hypothesis families. Transition has no lookback.
Persistence requires a complete strict bearish lookback. Each family has its own Holm correction and
is not pooled with the bullish grid.

#### Frozen bearish execution rules

- Signal date is not tradable; entry is the first stock session strictly after the signal.
- Holds are 30, 90, or 180 calendar days.
- Exit is the first available session on or after `entry + hold`.
- If that complete horizon does not exist, the trade is dropped. The final available price is never
  substituted for a requested future exit.
- Only one trade per ticker may be open inside one test cell. Later overlapping signals are counted
  and skipped.
- Raw short return is `-stock adjusted return`. Positive means the outright short made money.
- SPY-hedged short return is `SPY return - stock return`. Positive means the stock lagged SPY; the
  stock itself may still have risen, so this does not necessarily describe a profitable naked short.
- Adjusted prices include split/dividend economics. Borrow fees, locate availability, slippage,
  commissions, margin, and forced buy-ins are not modeled.

The transition family contains 12 tests: 2 bearish signal definitions x 3 holds x 2 outcomes. The
persistence family contains 48 tests: 2 signal definitions x 4 lookbacks x 3 holds x 2 outcomes.
Both require 15 ticker clusters, use the same ticker-cluster bootstrap as the bullish study, and use
the same `|t| >= 3` plus Holm `p < 0.05` display bar. A negative result that clears the bar is evidence
against the short strategy, not a profitable discovery. Thin cells have no inferential p-value but
remain in the frozen correction burden as `p=1`; their displayed p-values stay blank.

#### Bearish table columns

| Column | Meaning |
|---|---|
| Signals | Qualifying rating events before exclusions. |
| Complete | Trades with next-session entry and the full requested exit horizon. |
| Tickers | Unique ticker clusters represented by those complete trades. |
| Incomplete | Signals excluded because the full exit horizon or required price was unavailable. |
| Overlap | Signals skipped because a trade in the same ticker was already open for that cell. |
| Mean | Average gross return for the selected short outcome. Positive helps the short. |
| Profitable | Share of complete trades where that selected short outcome was positive. |
| Stock fell | Share where the stock's own adjusted return was negative. |
| Lagged SPY | Share where the stock returned less than SPY. |
| t / Holm p | Ticker-cluster evidence and family-wide multiple-testing correction. |

For newly crossing into Sell or Strong Sell, the saved outright-short results are:

|---|---:|---:|---:|---:|---:|---:|
| 30 days | 1,948 | 486 | 15 | -2.05% | 38.9% | 50.3% |

### Bullish persistence question

"Does staying at or above a bullish rating floor for a sustained lookback period predict a later
return above SPY, after correcting for searching many rules?"

This is the most statistically guarded screen in the application.

### The 48-rule pre-registered grid

```text
4 lookbacks x 3 holding periods x 2 floors x 2 dip tolerances = 48 cells
```

- Lookbacks: 3, 6, 12, and 18 months, represented as 63/126/252/378 trading days.
- Holds: 6, 12, and 18 months, represented as 126/252/378 trading days.
- Bullish+: rating is Buy or Strong Buy.
- Very bullish only: rating is Strong Buy.
- Strict: every day in the trailing window must meet the floor.
- 1% dip: at most 1% of trailing-window days may fall below the floor.

An entry occurs only on the first day a previously nonqualifying trailing window becomes qualifying.
The trade then holds for the fixed trading-day horizon and ignores later rating changes. Its tested
value is stock return minus SPY return over the same entry/exit dates.

### Evidence rules

- Minimum 15 distinct ticker clusters for a cell to be testable.
- Wild cluster bootstrap-t with ticker clusters and 4,999 replications in the current Python run.
- Discovery requires `|t| >= 3.0` and Holm-corrected `p < 0.05`.
- Holm correction treats the testable grid as one family.
- Benjamini-Hochberg p-values are also exported but Holm controls the displayed discovery decision.

### Columns

| Column | Meaning |
|---|---|
| Lookback | Required prior persistence period. |
| Hold | Fixed forward holding period. |
| Floor | Minimum qualifying rating group. |
| Dip tolerance | Allowed fraction of lookback days below the floor. |
| Trades | Number of qualifying entry events with complete future data. |
| Tickers | Number of distinct ticker clusters. |
| Mean excess | Average stock return minus SPY, in percentage points. |
| t | Cluster-robust signal-to-noise statistic. |
| p raw | Uncorrected probability under the null. |
| p Holm | Multiple-testing-corrected probability. |
| Status | Too thin, Clears bar, or No edge. |

### $100 table

The table translates one average trade into dollars. It is not a compounded portfolio simulation.
For example, `$117.92` means the average raw stock return for that rule would turn one $100 trade
into $117.92 over the stated hold period.

### Concentration check

Shows how much total excess return comes from the best 1, 2, 3, 5, or 8 trades and what the mean
would be without them. A rule carried by a few extreme trades is fragile.

### Placebo control

Random tickers are selected over the same entry and exit dates. This asks whether the rating selected
better stocks or whether almost any stock in the same period/universe would have done as well.

A cell can clear the t/Holm discovery bar and still fail the placebo control. In that case the
correct conclusion is that the observed return looks like a period or universe effect, not evidence
that the rating selected winners.

- 700 tickers;
- 515,174 price rows;
- 27,475 rating events;
- stock and ETF data from 2023-07-31 through 2026-08-07;

## 6.8 Portfolio

### Question answered

"If I repeatedly bought a basket of the highest-scoring currently eligible stocks, sold names that
stopped qualifying, and replaced them, how would that basket have performed against SPY and against
owning every eligible stock?"

This screen is a portfolio simulation, not the same engine as Stocks, Strong Buy trust, Prediction
accuracy, or Research lab.

### Explore controls

| Control | Meaning |
|---|---|
| Start/end | Calendar boundaries of the simulation. |
| Portfolio size | Maximum number of ranked holdings, from 1 to 100 in the UI. |
| Strong Buy only | Only Strong Buy records qualify. |
| Bullish+ | Buy and Strong Buy records qualify. |
| Weekly/monthly/quarterly | How often the full target list and weights are rebuilt. |
| Equal weight | Each buyable target receives the same target weight. |
| Score weighted | Target weights are proportional to positive Quant Score. |
| Sell on drop | Schedule a sale when an existing holding stops qualifying. |
| Sell at rebalance | Retain it until it drops out of the target at the next rebalance. |
| Maximum hold | Optional hard calendar-day cap: none, 90, 180, or 365 in manual Explore. |

### Daily simulation sequence

For each available date in the aligned imported rating calendar:

1. Mark open positions to that date's available price; carry the last price when a ticker has no
   new price.
2. Execute buy/sell decisions created at the previous date's close.
3. Evaluate current sell rules.
4. On a rebalance date, rank all eligible names by Quant Score and select the requested count.
5. If a position was sold between rebalances, attempt to replace it immediately with the best
   currently qualifying name not already retained.
6. Record portfolio value and drawdown.

A rating more than 10 calendar days old is treated as stale and therefore not currently eligible.
This can trigger a `rating-drop` exit even if there is no explicit new bearish rating. In plain
language, the engine treats "no sufficiently recent confirmation" as "no longer on the live list."

Signals are executed on the next available captured date, so the simulation does not buy at the
same close that produced the signal. If there is no later date, the pending trade is not executed.

### Rebalancing and weights

At each scheduled rebalance, the entire retained target book is returned to target weights. This
means:

- a new position is `BUY` / `open`;
- adding money to an existing underweight position is `ADD TO` / `add`;
- selling part of an overweight retained position is `TRIM` / `trim`;
- fully leaving a position is `SELL` / `close`.

The engine previously reweighted only new holdings, causing retained winners to drift far above
their intended equal weight. That bug has been fixed. Final-day weights can still differ from target
weights because prices move after the last rebalance.

### Sell reasons

| Timeline wording | Engine reason |
|---|---|
| Left the winners list | Rating became ineligible or stale while sell-on-drop was enabled. |
| Hit maximum holding period | Calendar-day hold cap fired. |
| Dropped out of selection | Removed from the ranked target at a scheduled rebalance. |
| Replacing a name that was sold | New qualifying position funded after another position closed. |

### Portfolio summary metrics

| Metric | Exact meaning |
|---|---|
| Portfolio return | Final simulated portfolio value minus the starting $100. Includes realized and unrealized positions. |
| Own everything | Return of the dynamic baseline that equally owns every currently eligible stock and updates at the selected rebalance cadence, with no rank/size selection. It is not a static buy-and-hold universe. |
| What picking added | Portfolio return minus the dynamic all-eligible pool return. This is the closest measure of the ranking/selection contribution. |
| SPY return | Adjusted SPY return from the simulation's first curve date to its last. |
| Above SPY | Portfolio return minus SPY return. It includes any advantage already embedded in the imported universe. |
| Max drawdown | Largest peak-to-later-value decline on available simulation dates. |
| Average holdings | Average selected target count at rebalance dates. |
| Trades | All execution records, including opens, closes, adds, and trims. |
| Sold on downgrade | Full exits whose reason is `rating-drop`. |

The simulation calendar is the union of imported ticker record dates, not an independently generated
exchange calendar. "Daily" means each available captured market date. Missing dates can understate
intraday or unobserved drawdowns.

### Portfolio activity timeline

The default timeline shows position decisions only:

- BUY: a new position opened.
- SELL: a position fully closed.

The optional "Every execution" mode also shows:

- ADD TO: an existing holding was topped up to target weight.
- TRIM: part of an existing holding was sold to return it to target weight.

The timeline is newest first. A SELL shows how many calendar days that position was held and why it
closed. The badge counts opens and full closes, not all rebalancing housekeeping.

### End-of-test holdings

"What you would be holding at the end" is only the open book on the final simulation date.

- Weight: current final value share.
- Opened: current position's entry date.
- Held: calendar days since that entry.
- Entry price: current position's cost basis, adjusted when topped up.
- Since entry: unrealized move of that still-open position.
- `too new`: held fewer than seven days, so a percentage would be uninformative.

This table does not explain the whole strategy return. The strategy return includes every earlier
position already sold. Therefore a +60% strategy can end with mostly 0%/`too new` holdings if the
last rebalance replaced the book immediately before the test ended.

### Find best / All tested configurations

The automated search currently tests:

```text
4 sizes (10, 20, 50, 100)
x 2 filters (Strong Buy only, Bullish+)
x 3 rebalances (weekly, monthly, quarterly)
x 2 weights (equal, score)
x 2 sell-on-drop settings
x 3 maximum holds (none, 90, 180)
= 288 configurations
```

Manual Explore supports 365 days, but the automated 288-grid does not currently include 365 days.

Configurations are sorted by `What picking added`, not total return or SPY excess. The UI renders
the first 15 rows. "Top" means the largest in-sample result among those 288 tests, not an unbiased
estimate of future return.

The search response contains configuration and summary data only. It deliberately strips daily
curves, holdings, rebalances, and trades, reducing the payload from roughly 105 MB to roughly 202 KB
on the current data. The compact summary retains executed open/close counts for expandable rows.
Pressing Use this re-fetches that one full configuration, then displays its timeline and holdings.

### Portfolio baselines and survivorship bias

The imported ticker universe was assembled from files exported later than much of the test period.
Companies that delisted or disappeared from coverage may be absent. This survivor universe can make
almost every portfolio look better than SPY.

That is why the screen emphasizes the all-eligible pool:

- `Above SPY` mixes universe effect and stock-picking effect.
- `What picking added` removes much of the shared universe effect.

It does not fully solve survivorship bias. A real-time historical universe containing every stock
that was eligible on each old date is still required for a genuinely investable backtest.

### Portfolio limitations

- No transaction costs or slippage.
- No real-time historical universe; survivor/coverage bias remains.
- The top result is selected after testing 288 configurations; no statistical correction or
  out-of-sample validation is applied to this search.
- The dynamic pool is not a static market index and changes with eligibility/rebalance cadence.
- Stale ratings older than 10 days are treated as ineligible.
- Available captured dates, not every exchange session/intraday point, determine the curve.
- There is no tax, liquidity, position-size, shorting, or capacity model.

## 7. Why screens can disagree

| Apparent contradiction | Explanation |
|---|---|
| Latest Strong Buy but poor trailing return | Latest rating is applied after some or all trailing return occurred. Use Prediction accuracy for forward testing. |
| Positive Strong Buy raw growth but negative robust mean | A few extreme winners can dominate compounded/raw results while the typical market-adjusted call is weak. |
| Portfolio beats SPY but not the pool | The imported survivor universe was strong; ranking added little or nothing beyond owning all eligible names. |
| Best portfolio is huge but median grid result is near zero | Selecting the maximum after hundreds of tests finds an unusually lucky configuration. |
| Strategy return high but final holdings near 0% | Profits came from earlier closed positions; final holdings were opened recently. |
| Stocks hit rate differs from Prediction accuracy | Stocks uses overlapping terminal-anchored daily records; Prediction accuracy uses rating episodes and fixed forward outcomes. |
| Rating groups look ordered but prediction is near chance | Rating groups are latest-rating/trailing-return cohorts; prediction tests point-in-time forward direction. |
| Research cell clears Holm but headline says no edge | The random-ticker placebo matched or beat it; statistical nonzero return was not specific to the rating rule. |
| Bearish stocks lag SPY but an outright short loses | Underperforming a rising market is not the same as falling. Only raw short return answers whether the naked short made money. |

## 8. Current evidence posture

The project should currently be described as a research prototype with increasingly honest controls,
not a proven trading strategy.

The strongest defensible saved finding is not "the rating works." The saved Research lab run found
some grid cells with nonzero excess return after Holm correction, but the strongest cell failed the
random-ticker placebo. Random stocks on the same dates performed at least as well most of the time.

The bearish research is clearer inside the observed survivor universe: no profitable raw or hedged
short rule clears its corrected bar. The strongest corrected findings run against shorting because
the stocks rose on average. This does not establish market-wide failure because the export contains
no real ticker series ending materially before the dataset end; missing delisted failures could be
important for a short strategy.

The Portfolio screen now separates:

- the return of the selected portfolio,
- SPY,
- the dynamic all-eligible pool, and
- the incremental return attributed to ranking/selection.

It also now simulates sell-on-drop behavior, full-book reweighting, next-date execution, daily
available-date drawdown, and an auditable open/add/trim/close timeline. These are important
engineering corrections, but they do not remove survivor-universe bias or transaction costs.

## 11. Guidance for future agents

Before changing a calculation:

1. Identify which question the screen claims to answer.
2. Do not silently replace a predictive test with a trading-policy test or vice versa.
3. Preserve point-in-time timing and next-date execution where already implemented.
4. Keep raw return and excess return explicitly separated.
5. Keep sample size, confidence intervals, outlier diagnostics, and placebo results visible.
6. Treat a searched maximum as exploratory unless corrected or validated out of sample.
7. Do not call the current ticker universe survivorship-bias-free.
8. Do not enable SQLite WAL in this workspace.
9. Update this README when a visible metric, rule, baseline, source, or limitation changes.
10. Append the work summary to `../progress.md` as required by `CLAUDE.md`.

When answering a screenshot question, quote the visible label and explain that exact metric. Do not
answer a question about `Since entry` using portfolio return, a question about `Avg return` using
Growth of $100, or a question about `Above SPY` using `What picking added`.
